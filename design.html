開発基盤のデータ設計

Claude が並列で進める作業を、1か所のデータで統制するための設計です。主役は「作業」で、リポジトリやブランチはその持ち物として扱います。人はこのデータを画面越しに見るだけで、必要なときだけ中身を追いに行きます。

考え方 全体像 6つのデータ 欄の定義 状態 ルール Claude と人の分担 回し方 フォルダ配置 固定するものと自由なもの 未確定と作る順番

考え方

この仕組みが守ることは8つです。データ定義もルールも、ここから出ています。

主役は作業

リポジトリもブランチも、作業の持ち物として扱います。全体の状況は、作業の一覧を見れば分かります。

データが原本、画面は表示

画面は何度作り直しても構いません。使う人が自由に書き換えてよいものです。

書き換えの入口は1つ

データを書き換えるのは hub コマンドだけです。Claude も MCP も、同じ入口を通ります。

作業は Claude、確認は人

操作は Claude が行います。人が挟まるのは、やり直しがきかない操作だけです。

確かめられる値は保存しない

Git に聞けば分かることは、聞くたびに確かめます。保存した値は、実際の状態とずれるからです。

登録の無いものはゴミ

置き場を厳しく決める代わりに、すべてをデータに登録します。登録が無ければ消してよいものです。

欄は平らに保つ

入れ子を作らず、複数あるものは別のデータにします。先回りした拡張は入れません。

仕組みとデータは別

配るのは仕組みだけです。データは環境ごとに手元へ置き、混ぜません。

全体像

作業は WSL の中で Claude Code が進めます。その状況はすべて「全体管理リポジトリ」にデータとして書かれます。人は Claude Desktop のアーティファクトだけを見て、アーティファクトはローカル MCP を通じてそのデータを読み書きします。

この資料が扱うのは、図の青い箱の中身です。ここが正しく保たれていれば、表示側は何度作り直しても失うものがありません。

6つのデータ

持つデータは6種類です。矢印は「持つ」または「指す」の向きで、どれも1件に対して複数がぶら下がります。

作業(主役) 場所に関するもの 人の承認 その他

「作業」は、ばらばらに生まれるブランチや HTML を束ねる札です。GitHub の Issue に近いものですが、1つのリポジトリに閉じず、複数のリポジトリと記録をまたいで束ねます。

欄の定義

どのデータも、入れ子を持たない平らな欄だけで定義します。1件を1つのテキストファイルとして持ちます。

会話では「作業に承認ゲートの一覧を持たせる」としていましたが、欄を平らに保つために、独立したデータに分けています。

状態

状態を持つのは4つです。破線の丸は、そこで役目を終える状態です。

作業進行中→終了→片付け済み
記録下書き→確定→共有
ToDo未着手→作業にした/完了/捨てた
承認ゲート未承認→承認済み
記録の状態置き場失ったら
下書き手元に置くだけ諦める
確定残すと決めたもの。データ用のリモートをつないだ環境では push するリモートをつないでいれば戻せる
共有claude.ai にも出す—

ルール

親と子は同じもの

親も子も同じ「作業」です。違いは parent_id に値があるかどうかだけです。子を独立させるときは、この欄を空にします。

作業場の持ち主は1つ

作業場は、それを切った作業だけが持ちます。作業が持つ作業場は0個でも複数でも構いません。読むだけなら作業場は要りません。

子が残る親は閉じられない

親を閉じる前に、子を1つずつ「終わらせる」「別の作業に吸収させる」「親から切り離す」のどれかにします。

閉じると片付けるは別

閉じるのは状態を変えるだけです。作業場を消すのは、ここにしか無い変更が無いと Git で確かめてからです。

自分の作業しか書かない

各セッションは、自分が担当する作業の配下だけを書き換え、自分が触ったファイルだけをコミットします。

共有の一覧は保存しない

作業の一覧や ToDo の一覧は、ファイルとして持ちません。表示のたびに1件ずつのファイルから組み立てます。

登録の無いものはゴミ

作業場も記録も、必ずデータに登録します。登録されていないフォルダは、消してよいものとして機械的に見つけられます。

ToDo は作業の手前の受け皿

ToDo は作業ではありません。作業にすると決めたときに、初めて作業が1件起きます。作業は ToDo を経由しなくても起こせます。

親子の例

作業名とリポジトリ名は説明用の例です。

Claude と人の分担

操作は基本的にすべて Claude が行います。人が挟まるのは、やり直しがきかない操作だけです。その箇所は、作業を起こす時点で承認ゲートとして登録され、画面に「承認待ち」として並びます。

Claude が自分でやる人が承認する
作業を起こす、子に分ける、閉じるリモートへの push
作業場を切る記録を「確定」に上げる(push を伴う)
記録を書く、手元でコミットするclaude.ai への共有
ToDo を足す、状態を変える中身が残っている作業場を消す
中身が空だと確かめられた作業場を消すGitHub のリポジトリやブランチを作る・消す

書き手は3者います。裏で動く Claude Code、Claude Desktop 経由の MCP、そして直接ファイルを開くあなたです。データの形を崩さないために、書き換えは共通のコマンド群を通して行います。提案

回し方

流れは2つあり、別々に回ります。中心は作業の流れで、いつでも起こせて、いくつでも並列に進みます。ToDo の流れは、その手前にある受け皿です。2つがつながるのは、作業の途中で ToDo が出るときと、ToDo を作業にするときの2か所だけです。

作業は ToDo を経由しなくても起こせます。「これをやって」と頼めば、その場で作業が1件起きます。ToDo は、いますぐ作業にするほどではないものを取っておく場所です。

場面きっかけやること
作業を起こす人が頼んだとき。または ToDo を作業にすると決めたとき目的を書き、必要になる承認をゲートとして登録する
作業を進める作業が進行中のあいだ作業場を切る。記録を書く。大きくなったら子に分ける。引っかかりは ToDo に残す
承認に答える承認待ちが出たとき人がゲートを承認する。承認されるまで、その操作は止まる
閉じる目的を果たした、吸収された、やめた、のどれか子を先に整理する。その作業から出た ToDo を仕分ける
片付ける作業を閉じたあと作業場を1つずつ確かめて消す。下書きは確定に上げるか捨てる。全部済むと「片付け済み」になる
ToDo の場面きっかけやること
残す作業の途中で引っかかったとき。ふと思いついたとき一言で書く。やる日が決まっていれば日付を入れる
仕分ける好きなとき。回数も頻度も決めない1つずつ「作業にする / そのまま済ませる / 捨てる / 残す」に分ける

フォルダ配置

仕組みとデータは別々に持ちます。GitHub に置いて配るのは仕組みだけで、データは環境ごとに手元へ置きます。同じ仕組みを、プライベートでも社用でも clone して使えます。

仕組みデータ
中身hub コマンド、この設計資料、Claude 向けの決まり、導入手順作業、作業場、記録、ToDo、承認ゲート、リポジトリの登録
置き場~/dev/hub(clone したもの)~/dev/data(全体管理リポジトリ)
環境をまたいで同じものを使う混ぜない

場所はデータの path と file が知っているので、フォルダの規約で厳しく縛る必要はありません。固定するのは、全体管理リポジトリの場所だけです。下は既定の配置です。

~/dev/
  hub/                          仕組み(このリポジトリを clone したもの)
  data/                         全体管理リポジトリ(データ。ここだけ固定)
    tasks/<作業ID>/              作業1件のデータと、その記録の HTML
    todos/                      ToDo(1件1ファイル)
    repos/                      リポジトリの登録情報
  repos/<リポジトリ名>/           コードの本体(ここでは直接作業しない)
  work/<作業ID>/<リポジトリ名>/   作業場

作業場は、リポジトリの下ではなく作業の下に置きます。人が追うときは、作業の番号を1つ知っていれば、data/tasks/ で経緯が、work/ でコードが見つかります。

固定するものと自由なもの

この仕組みが約束するのは、データの形と回し方です。それ以外は、使う人が書き換えて構いません。

固定する自由にしてよい
6つのデータと、その欄・状態の値画面(全体・個別作業・ToDo)の見た目と作り
ルール(親子、持ち主、閉じると片付ける、承認)コードのリポジトリと作業場の置き場
書き換えの入口が hub コマンドだけであることClaude 向けの決まりの言い回し
コマンドの名前と、--json で返す形仕分けの頻度や、1日の進め方

画面と MCP は、hub コマンドを呼ぶだけの薄い層にします。コマンドと返す形が変わらなければ、画面をどう書き換えても壊れません。

欄を変えるときの決まり 提案

  • 欄を足すだけなら、版の番号は変えません。古いファイルは、その欄が空のものとして読みます。
  • 欄の意味を変える、欄を消す、状態の値を変えるときは、版の番号を上げ、古いファイルを直すコマンドを一緒に用意します。

作る前に固めた4点

データ定義は、あとから変えにくい部分です。欄を平らに保つ方針はそのままにして、次の4点を先に決めました。

項目案理由
番号の付け方 提案種類の頭文字 + 日付 + 短い乱数(例 t-20261122-a3f)連番にすると、並列で同時に起こしたときに同じ番号が付く
版の番号 提案すべてのファイルに schema: 1 を入れる将来欄を変えたとき、古い形のファイルを見分けて直せる
状態の値この資料の「状態」に挙げた値だけを使う自由に書けると、表示側が集計できなくなる
平らな欄欄の中に入れ子や一覧を持たせない。複数あるものは別のデータにする入れ子は、並列で書いたときにぶつかりやすく、後から形を変えにくい

未確定と作る順番

確かめていないこと 未確認

  • アーティファクトから、ローカル MCP の書き込みを呼べるか。
  • Windows 側の Claude Desktop から、WSL の中の MCP に届くか。
  • アーティファクトから Claude のセッションを起こせるか。別の道として、MCP から WSL 側の Claude Code を起動する形があります。
  • 承認を強制する設定の正確な書き方。

後回しにしたこと

  • データを別のマシンへ持ち出すこと。必要になったら、データの入れ物を自分の非公開リポジトリへ push すれば足ります。
  • サブ PC からの接続。
  • リポジトリ固有の判断を、そのリポジトリの中に置くかどうか。いまはすべて全体管理リポジトリに集めます。

作る順番

  1. 全体管理リポジトリと、データを書き換える共通のコマンド群を作る。(済み)
  2. アーティファクトとローカル MCP がつながるかを小さく試す。
  3. MCP を作る。中身は 1 のコマンド群を呼ぶだけにする。
  4. 全体作業・個別作業・ToDo の3つの画面を作る。
  5. アーティファクトからのセッション起動。
