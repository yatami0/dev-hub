開発基盤のデータ設計

Claude が並列で進める作業を、1か所のデータで統制するための設計です。主役は「作業」で、リポジトリやブランチは作業に所属するものとして扱います。人はこのデータを画面越しに見るだけで、必要なときだけ中身を追いに行きます。

用語 考え方 全体像 6つのデータ 項目の定義 状態 ルール Claude と人の分担 回し方 セッションと認証 フォルダ配置 固定するものと自由なもの 未確定と作る順番

考え方

この仕組みが守ることは10個です。データ定義もルールも、ここから出ています。

主役は作業

リポジトリもブランチも、作業に所属するものとして扱います。全体の状況は、作業の一覧を見れば分かります。

データが原本、画面は表示

画面は何度作り直しても構いません。使う人が自由に書き換えてよいものです。

書き換えは hub コマンド経由のみ

データを書き換えるのは hub コマンドだけです。Claude も MCP も、このコマンドを通ります。

作業は Claude、確認は人

操作は Claude が行います。人が挟まるのは、やり直しがきかない操作だけです。

Git から分かる情報は保存しない

Git から分かる情報は、必要なたびに取得します。保存した値は、実際の状態とずれるからです。

未登録のものは削除対象

置き場を厳しく決める代わりに、すべてをデータに登録します。未登録のファイルやフォルダは、削除対象として扱います。

項目は入れ子にしない

入れ子を作らず、複数あるものは別のデータにします。先回りした拡張は入れません。

仕組みとデータは別

配るのは仕組みだけです。データは環境ごとにローカルへ置き、混ぜません。

鍵は渡さず、用事を代行する

認証が要る操作は hub が実行し、Claude には結果だけを返します。認証情報そのものを渡す道具は作りません。

秘密はデータに入れない

データリポジトリに入るのは、プロファイルの名前だけです。トークンや認証ファイルは Git の管理の外に置きます。

全体像

作業は WSL の中で Claude Code が進めます。その状況はすべて「データリポジトリ」にデータとして書かれます。人は Claude Desktop のアーティファクトだけを見て、アーティファクトはローカル MCP を通じてそのデータを読み書きします。

この資料が扱うのは、データリポジトリの中身です。ここが正しく保たれていれば、画面は何度作り直しても失うものがありません。

6つのデータ

中心になるデータは6種類です。このほかに、hub が起動した実行を残す「セッション」があります(「項目の定義」を参照)。矢印は「持つ」または「指す」の向きで、どれも1件に対して複数がぶら下がります。

作業(主役) 場所に関するもの 人の承認 その他

「作業」は、ばらばらに生まれるブランチや HTML を束ねる単位です。GitHub の Issue に近いものですが、1つのリポジトリに閉じず、複数のリポジトリと記録をまたいで束ねます。

ルール

親と子は同じもの

親も子も同じ「作業」です。違いは parent_id に値があるかどうかだけです。子を独立させるときは、この項目を空にします。

作業場は1つの作業に所属する

作業場は、それを作った作業に所属します。作業が持つ作業場は0個でも複数でも構いません。読むだけなら作業場は要りません。

子が進行中の親は終了できない

子の作業が進行中のあいだ、親の作業は終了できません。先に、子を1つずつ「終了する」「別の作業に吸収させる」「親から切り離す」のどれかにします。

終了と片付けは別の操作

終了は状態を変えるだけです。作業場を削除するのは、未反映の変更が無いと Git で確かめてからです。

自分の作業しか書かない

各セッションは、自分が担当する作業の配下だけを書き換え、自分が触ったファイルだけをコミットします。

一覧のファイルは保存しない

作業の一覧や ToDo の一覧は、ファイルとして持ちません。表示のたびに1件ずつのファイルから組み立てます。

未登録のものは削除対象

作業場も記録も、必ずデータに登録します。未登録のフォルダは、削除対象として機械的に見つけられます。

ToDo は作業にする前の置き場

ToDo は作業ではありません。作業にすると決めたときに、初めて作業が1件できます。作業は ToDo を経由しなくても作れます。

回し方

流れは2つあり、別々に回ります。中心は作業の流れで、いつでも作れて、いくつでも並列に進みます。ToDo の流れは、作業にする前のものを置く場所です。2つがつながるのは、作業の途中で ToDo が出るときと、ToDo を作業にするときの2か所だけです。

作業は ToDo を経由しなくても作れます。「これをやって」と頼めば、その場で作業が1件できます。ToDo は、いますぐ作業にするほどではないものを取っておく場所です。

セッションと認証

人は Claude Desktop から作業を頼み、hub が WSL の中で Claude Code のセッションを起動します。プロファイル、セッションの起動と再開、承認の待ち行列、hub による push は hub コマンドに入っています。MCP と、外部のサービスの認証を hub が持つ部分は、まだ作っていません。

起動の流れ

  • セッションは対話なしで起動します。指示を1つ渡して実行し、結果とセッションの ID を受け取ります。続きは同じセッションを再開して渡します。再開してもセッションの ID は変わりません。
  • hub は実行のたびに、結果に入っている「拒否された操作の一覧」を読みます。拒否があってもセッションはエラーにならず最後まで進むので、エラーの有無だけでは気づけません。
  • 起動のとき、環境変数 CLAUDE_CONFIG_DIR でプロファイルを指定します。
  • 途中で口を挟みたい作業のために、あとから Remote Control でつなぐ方式を足せます。

プロファイル

プロファイルは、Claude Code の設定フォルダを丸ごと1つにまとめたものです。入っているスキル、プラグイン、MCP、権限の設定、そして Claude のアカウントの認証が、プロファイルごとに分かれます。プロファイルを1つ選ぶと、「何を使えるか」と「誰として動くか」が同時に決まります。

  • プロファイルはデータとして保存しません。フォルダを見れば一覧が分かるので、必要なたびに読み取ります。
  • 置き場は ~/dev/profiles/<名前>/ です。既定のプロファイルの名前は default です。Git の管理の外に置きます。
  • 共通のスキルやエージェントは1か所に置き、各プロファイルからリンクします。(未実装)
  • プライベートと社用は、必ずプロファイルを分けます。
選ぶ段内容
既定のプロファイル何も指定しなければ、これで起動する
リポジトリの指定「このリポジトリはこのプロファイルで」と決めておける。食い違う作業は、作業場を作る時点で止まる
作業での指定作業を作るときに選ぶ。既定より優先する

認証情報は hub が持ち、Claude のセッションには渡しません。Claude は hub に用事を頼み、結果だけを受け取ります。

  • 外部のサービスの認証は、プロファイルの名前ごとに hub が持ちます。作業のプロファイルに合うものを使います。
  • どうしても Claude 自身に通信させたいときは、対象と権限を絞った読み取り専用の鍵だけを渡します。
  • プロファイルに入れた MCP は Claude がそのまま使えるので、作業に必要なものだけを入れます。

承認は待ち行列になる

対話なしのセッションは、途中で人に確認できません。そこで、やり直しがきかない操作は Claude ではなく hub が実行します。

  1. Claude は、push などが必要になったら承認ゲートを登録して止まる。(hub push、hub record confirm など)
  2. 人が承認する。(hub gate approve)
  3. hub が承認の記録を書き、続けてその操作を実行する。成功したら「実行済み」になる。失敗したら「承認済み」のまま残り、もう一度承認のコマンドを実行すると再実行する。
  4. 続きがあれば、人か hub がセッションを再開する。
操作承認されたとき
pushhub が、登録されたリモートへ、その作業場のブランチを push する
記録の確定hub が記録を「確定」にする
作業場の強制削除hub が作業場を削除する
公開、リモートの作成・削除hub は実行しない。承認済みであることを確かめてから、hub の外で行う

承認の記録は、セッションから読めますが、書けません。書き込みは、サンドボックスと禁止の設定の両方で止めています。読み取りまで禁止すると、サンドボックスの中では空の場所に差し替わり、書き込みが通ったように見えてしまうので、読み取りは禁止しません。

「Claude と人の分担」の表で人が承認するとしている操作は、この形になると、実行するのも hub になります。いま入れている「push のたびに確認する設定」は、役目を終えます。

禁止した操作を止める3層

層仕組み強さ
認証を渡さない書き込める認証を Claude のセッションに渡さない一番強い。認証が無ければ、コマンドをどう書いても失敗する
禁止の設定プロファイルの設定で、特定のコマンドや道具を禁止する。Read / Edit / Write の道具から、認証情報の置き場と承認の記録を守るのもこの層中くらい。書き方を変えると一致しない場合がある
サンドボックスBash から、認証情報の置き場と承認の記録に触れないようにする。外部との通信も止める上の2つを成り立たせる条件。WSL2 で動くことを確認済み。効くのは Bash だけ

サンドボックスと禁止の設定は、必ず両方を入れます。サンドボックスは Bash にしか効かず、禁止の設定は Bash の中で動くコマンドには効かないからです。プロファイルに入れる設定は次のとおりです。

設定値理由
sandbox.enabledtrueBash をサンドボックスの中で動かす
sandbox.failIfUnavailabletrue既定では、部品(bubblewrap と socat)が足りないとサンドボックス無しで動いてしまう
sandbox.allowUnsandboxedCommandsfalseサンドボックスの外で実行し直す道をふさぐ
sandbox.filesystem.denyRead認証情報の置き場既定では、認証ファイルを Bash から読める
sandbox.filesystem.allowWriteデータリポジトリ、作業場の元のリポジトリの .gitセッションの中から hub コマンドとコミットを使えるようにする
sandbox.filesystem.denyWrite承認の記録、hub リポジトリ、各 .git の config と hooks許可と禁止が重なったときは、禁止が勝つ。Git の設定とフックは、hub があとで Git を動かすときに実行されうるので止める
permissions.denyEdit(...) を承認の記録と hub リポジトリに、Read(...) を認証情報に、Bash(git push*) と Bash(hub gate approve*)Read / Edit / Write の道具を止める。Read の禁止は書き込みも止める

この設定は、セッションを起動するたびに hub が組み立てて渡します。中身は hub session settings で見られます。hub 自身も、Git を動かすときはフックを無効にします。

サンドボックスの既定では、実行した場所の中と /tmp には書けて、ホームの下のそれ以外には書けません。外部との通信は、許可した宛先だけが通ります。

作業場の中での失敗(ファイルを消す、的外れなコミット)は止めません。作業場は使い捨てで Git の履歴もあるので、戻せることで守ります。

コアと拡張

hub の MCP は1つだけです。リポジトリや外部のサービスが増えても、MCP は増えません。中の道具は2層に分かれます。

コア拡張
扱うものこの資料のデータhub が持っていない情報。外部のサービス、環境の状態
書き込みするしない。書き込みたいときは、コアの操作か承認ゲートを通す
置き場hub リポジトリ環境ごと。hub リポジトリが配るのは、拡張を足す仕組みだけ
例作業を作る、ToDo を足す、承認するIssue を取る、Redmine のチケットを取る、プロファイルの中身を見る

道具の入口は2つあります。人は Claude Desktop から MCP 経由で呼び、WSL の中の Claude のセッションは hub コマンドとして呼びます。中のロジックは同じです。

  • MCP の本体は tool/mcp.mjs です。コアの道具は、hub コマンドと1対1で対応します。名前は、コマンドの空白を _ に替えたものです(hub task new は task_new)。
  • 拡張は、環境ごとに ~/dev/extensions/*.mjs へ置きます。MCP が起動のときに読み込み、名前の先頭に ext_ を付けて並べます。
  • 承認(gate_approve)も MCP から呼べます。人がはっきり承認したときだけ呼ぶ道具です。Claude Desktop 側で、この道具を「毎回確認する」にしておきます。
  • セッションの起動と再開は、終わるまで待ってから結果を返します。長い作業では、Claude Desktop 側の待ち時間を超える可能性があります。(未確認)
拡張の形(~/dev/extensions/sample.mjs)
export const tools = [{
  name: 'hello',                          MCP では ext_hello になる
  description: '説明',
  inputSchema: { type: 'object', properties: { who: { type: 'string' } } },
  run: ({ who }) => ({ hello: who }),     文字列か、JSON にできる値を返す。書き込みはしない
}];

追加内容

試して確かめたこと

  • 対話なしで実行すると、結果、セッションの ID、エラーの有無、拒否された操作の一覧が、データとして返る。
  • 空のプロファイルを指定すると「ログインしていません」になる。認証はプロファイルごとに分かれている。
  • 指定したフォルダに、設定、セッションの履歴、認証情報が作られる。履歴は実行した場所ごとに分かれる。
  • 無人の実行には、claude setup-token で作ったトークンを CLAUDE_CODE_OAUTH_TOKEN で渡す方法が案内されている。
  • 再開すると、前の文脈を覚えたまま続く。セッションの ID は変わらない。別のフォルダからも再開できる。
  • 禁止した操作、確認が要る操作、許可していない操作は、どれもその操作だけが拒否される。セッションは止まらず、拒否された操作はコマンドの中身つきで結果に入る。
  • サンドボックスは WSL2 で動く。Bash からの読み書きを場所ごとに止められる。Read / Write の道具は、禁止の設定で止められる。
  • プロファイルを CLAUDE_CONFIG_DIR で指定したセッションも、再開できる。
  • サンドボックスの中から hub コマンドでデータを書ける。承認の記録、hub リポジトリ、Git の設定とフックには書けない。
  • Windows 側の Claude Desktop から、wsl.exe 経由で WSL の中の MCP に届く。読み取りも書き込みも通る。
  • アーティファクトから、手元の hub の MCP を読み書きできる。画面から足した ToDo が、データリポジトリに入ってコミットされた。
  • アーティファクトが手元の MCP を呼べるのは、持ち主が Claude のデスクトップアプリで開いたときだけ。ファイルを直接開いた場合や、ブラウザで開いた場合は呼べない。
  • 読むだけの印が無い道具は、呼ぶたびにアプリが確認を出す。印を付けた道具で確認が出なくなるかは、まだ確かめていない。

試した内容と結果の詳細は、作業 t-20261122-081 の記録「対話なしセッションの3点を試した結果」にあります。

フォルダ配置

仕組みとデータは別々に持ちます。GitHub に置いて配るのは仕組みだけで、データは環境ごとにローカルへ置きます。同じ仕組みを、プライベートでも社用でも clone して使えます。

仕組みデータ
中身hub コマンド、この設計資料、Claude 向けのルール、導入手順作業、作業場、記録、ToDo、承認ゲート、リポジトリの登録
置き場~/dev/hub(clone したもの)~/dev/data(データリポジトリ)
環境をまたいで同じものを使う混ぜない

場所はデータの path と file が知っているので、フォルダの規約で厳しく縛る必要はありません。固定するのは、データリポジトリの場所だけです。下は既定の配置です。

~/dev/
  hub/                          仕組み(このリポジトリを clone したもの)
  data/                         データリポジトリ(データ。ここだけ固定)
    tasks/<作業ID>/              作業1件のデータと、その記録の HTML
    approvals/                  承認の記録(セッションからは書けない)
    todos/                      ToDo(1件1ファイル)
    repos/                      リポジトリの登録情報
  repos/<リポジトリ名>/           コードの本体(ここでは直接作業しない)
  work/<作業ID>/<リポジトリ名>/   作業場
  profiles/<名前>/               プロファイル(Git の管理の外)

作業場は、リポジトリの下ではなく作業の下に置きます。人が追うときは、作業の IDを1つ知っていれば、data/tasks/ で経緯が、work/ でコードが見つかります。

固定するものと自由なもの

この仕組みが約束するのは、データの形と回し方です。それ以外は、使う人が書き換えて構いません。

固定する自由にしてよい
6つのデータと、その項目・状態の値画面(全体・個別作業・ToDo)の見た目と作り
ルール(親子、所属、終了と片付け、承認)コードのリポジトリと作業場の置き場
書き換えが hub コマンド経由だけであることClaude 向けのルールの言い回し
コマンドの名前と、--json で返す形仕分けの頻度や、1日の進め方
コアの道具(6つのデータを読み書きするもの)拡張の道具(外部のサービスや環境の状態を読むもの。環境ごとに足す)

画面と MCP は、hub コマンドを呼ぶだけの薄い層にします。コマンドと返す形が変わらなければ、画面をどう書き換えても壊れません。

項目を変えるときのルール 提案

  • 項目を足すだけなら、スキーマのバージョンは変えません。古いファイルは、その項目が空のものとして読みます。
  • 項目の意味を変える、項目を削除する、状態の値を変えるときは、スキーマのバージョンを上げ、古いファイルを直すコマンドを一緒に用意します。

作る前に固めた4点

データ定義は、あとから変えにくい部分です。項目を入れ子にしない方針はそのままにして、次の4点を先に決めました。

項目案理由
ID の付け方 提案種類の頭文字 + 日付 + 短い乱数(例 t-20261122-a3f)連番にすると、並列で同時に作ったときに同じ ID が付く
スキーマのバージョン 提案すべてのファイルに schema: 1 を入れる将来項目を変えたとき、古い形のファイルを見分けて直せる
状態の値この資料の「状態」に挙げた値だけを使う自由に書けると、画面が集計できなくなる
入れ子にしない項目の中に入れ子や一覧を持たせない。複数あるものは別のデータにする入れ子は、並列で書いたときにぶつかりやすく、後から形を変えにくい
